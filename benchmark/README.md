# Benchmark

Одинаковая проверка каждой версии поиска и ответа. Набор вопросов и эталонов фиксируется до настройки поиска, затем выдача и ответы сравниваются с ним.

## Состав

- `questions.json` — 10 обычных вопросов и 5 вопросов-ловушек;
- `results/` — сохранённые прогоны;
- корпус — `corpus/docs.jsonl`, 30 документов D01–D30.

## Формат `questions.json`

Список объектов. Обычный вопрос:

```json
{
  "id": "Q01",
  "type": "normal",
  "question": "Можно ли передать персональные данные клиентов подрядчику, который обучает нашу модель?",
  "relevant": ["D04", "D15", "D22"],
  "reference": "Можно по поручению оператора с договором, где указаны цели и меры защиты; по GDPR — договор с процессором по ст. 28."
}
```

Ловушка:

```json
{
  "id": "T01",
  "type": "trap",
  "question": "Какой штраф по КоАП грозит за утечку персональных данных?",
  "relevant": [],
  "reference": "NO_ANSWER"
}
```

Примеры условные: ID и формулировки появятся после сборки корпуса.

## Правила составления вопросов

- У каждого обычного вопроса не меньше трёх релевантных документов. Релевантные документы размечает человек.
- Вопросы равномерно покрывают корпус: каждый акт и каждая тема из `spec/tech/rag.md` встречаются хотя бы в одном вопросе.
- Вопросы формулируются своими словами, как спросил бы продакт или разработчик, а не копированием фрагментов статей.
- Эталон — короткий ответ, который можно проверить по релевантным документам.
- Ловушки правдоподобны и близки к теме, но ответа в корпусе нет: штрафы, сроки уведомления регулятора, законы других стран, нормы вне выбранных статей.
- Вопросы и эталоны пишутся до настройки поиска и после этого не меняются. Для подбора `MIN_SCORE` используется отдельный черновой набор.

## Метрики

Поиск — по 10 обычным вопросам, глубина `k = 5`:

- **Recall@5** — доля релевантных документов, найденных в первых пяти, усреднённая по вопросам:
  Recall@5 = (1 / |Q|) · Σ |R(q) ∩ Top5(q)| / |R(q)|.
- **MRR** — средний обратный ранг первого релевантного документа:
  MRR = (1 / |Q|) · Σ 1 / rank(q); если в первых пяти релевантного нет, слагаемое равно 0.

Ответ — по всем 15 вопросам:

- **Accuracy** — доля полностью правильных ответов из 10 обычных. Ответ правильный, если совпадает по смыслу с эталоном и не содержит утверждений, которых нет в документах. Оценивается вручную.
- **Correct Rejection Rate** — доля корректных отказов из 5 ловушек. Любой ответ по существу, догадка или выдуманная норма — ошибка.

Ловушки в метрики поиска не входят.

## Запуск

Из корня проекта:

```bash
python -m benchmark                  # поиск: Recall@5 и MRR по обычным вопросам
python -m benchmark --answers        # плюс ответы и отказы через API (run_search) по всем 15 вопросам
```

Параметры для экспериментов (меняйте по одному):

| Параметр | Что делает |
|---|---|
| `--no-lemmatize` | без лемматизации |
| `--no-stopwords` | без удаления стоп-слов |
| `--no-synonyms` | без словаря синонимов |
| `--k1 1.5`, `--b 0.5` | параметры BM25 (по умолчанию 1,2 и 0,75) |
| `--k 5` | глубина Recall@k и MRR |
| `--name базовый` | описание прогона в имени файла результата |
| `--no-save` | не сохранять результат |
| `--questions путь` | другой файл вопросов (например, черновой набор для подбора `MIN_SCORE`) |
| `--sweep` | перебор `k₁` (1,2; 1,5; 1,8; 2,0) и `b` (0,5; 0,75; 1,0), таблица Recall@k и MRR |
| `--thresholds` | таблица порогов `MIN_SCORE`: сколько обычных вопросов проходит порог и сколько вопросов без ответа им отсекается |

### Подбор `MIN_SCORE`

Порог подбирается на отдельном черновом наборе `draft_questions.json` (4 обычных вопроса и 4 без ответа), а не на основном, чтобы итоговая Correct Rejection Rate не была подогнана:

```bash
python -m benchmark --questions benchmark/draft_questions.json --thresholds --no-save
```

Замечания «нужно 10 + 5» и «меньше 3 релевантных» для чернового набора ожидаемы и не мешают.

Порог `MIN_SCORE` берётся из переменной окружения `RAG_MIN_SCORE`, как в API. Скрипт проверяет набор вопросов (10 + 5, не меньше трёх релевантных, ID есть в корпусе) и выводит замечания со знаком `!`.

### Accuracy и Correct Rejection Rate

- **Correct Rejection Rate** считается автоматически: ловушка отклонена, если API вернул статус `insufficient` (порог или `NO_ANSWER` модели).
- **Accuracy** размечается вручную: в сохранённом файле у каждого обычного вопроса есть поле `"correct": null` — поставьте `true` или `false`, сравнив ответ с эталоном. Затем пересчитайте метрики:

```bash
python -m benchmark --rescore benchmark/results/ГГГГ-ММ-ДД_описание.json
```

## Что сохраняется в `results/`

Один прогон — один файл `ГГГГ-ММ-ДД_описание.json`. В нём настройки (предобработка, `k₁`, `b`, `k`, `MIN_SCORE`), замечания к набору вопросов, выдача по каждому вопросу (ID и баллы, recall и обратный ранг), при `--answers` — статус, ответ модели и процитированные ID, и посчитанные метрики.

## Эксперименты

Меняется одна настройка за раз, корпус, вопросы и `k = 5` те же. Основные цифры — по проверенной разметке (v2, `labeling_check.md`); вклад отдельных шагов предобработки измерялся по первой разметке (v1) и приведён для сравнения.

| Прогон | Что изменено | Разметка | Recall@5 | MRR |
|---|---|---|---|---|
| базовый | без лемматизации; стоп-слова и синонимы включены; `k₁ = 1,2`, `b = 0,75` | v1 | 0,283 | 0,470 |
| + лемматизация | `pymorphy3` | v1 | 0,367 | 0,592 |
| + стоп-слова вопросов | «можно», «нужно», «наш», «какой» и др. | v1 | 0,400 | 0,562 |
| **базовый** | как выше, без лемматизации | **v2** | **0,290** | **0,490** |
| **итоговая конфигурация** | лемматизация, стоп-слова (с вопросными), синонимы, `k₁ = 1,2`, `b = 0,75` | **v2** | **0,370** | **0,600** |
| подбор `k₁`, `b` | `k₁` 1,2–2,0, `b` 0,5–1,0 (`--sweep`) | v2 | 0,370 при всех парах | 0,542–0,600 |

Выводы по экспериментам:

- Лемматизация — самое заметное улучшение: Recall@5 +0,08, MRR +0,11–0,12 (на обеих разметках). Вопросы сформулированы своими словами, и без приведения к начальной форме «подрядчику» и «подрядчик» — разные термы.
- Стоп-слова вопросов на разметке v1 подняли Recall@5 (0,367 → 0,400) и немного снизили MRR (0,592 → 0,562). Оставлены: Recall важнее для контекста LLM, шаг не привязан к конкретным вопросам.
- Параметры BM25 почти не влияют: Recall@5 одинаков при всех 12 парах; MRR равен 0,600 при любом `k₁` и `b ≤ 0,75` и падает до 0,54–0,56 при `b = 1,0` (полная нормализация по длине сильнее штрафует длинные статьи). Стандартные `k₁ = 1,2`, `b = 0,75` входят в лучшую группу и оставлены.
- Проверка разметки снизила Recall@5 итоговой конфигурации с 0,400 до 0,370: в разметку добавлены документы, которые поиск не находил (D04 в Q03, D28 в Q04, D03 в Q07, D06 в Q09). Это ожидаемо: разметка не подгонялась под выдачу.

## Разбор ошибок

Разбор по прогону `2026-11-23_итог-v2` (проверенная разметка; лемматизация, стоп-слова, синонимы, `k₁ = 1,2`, `b = 0,75`). Колонки — где потеряна информация (схема занятия 3). «В базе»: все размеченные тексты в корпусе есть (ограничения корпуса — в `labeling_check.md`: нет ст. 27 и Приложения III AI Act). «В контексте» и «В ответе» заполняются после подключения настоящей LLM.

| Вопрос | Recall@5 | Найдено (позиция) | Потеряно в поиске | Причина |
|---|---|---|---|---|
| Q01 согласие или другие основания | 0,50 | D11 (1), D13 (3) | D03, D05 | в 152-ФЗ основания названы «случаями» («обработка допускается в следующих случаях»), а не «основаниями»; D03 длинный (7 тыс. символов) и проигрывает из-за нормализации по длине; на 2-м месте шум — D24 (AI Act) |
| Q02 договор с подрядчиком | 0,33 | D17 (3) | D04, D16 | бытовое «подрядчик» против юридических «лицо, осуществляющее обработку по поручению» и «процессор»; первым идёт D03 — много общих слов «обработка», «персональные данные» |
| Q03 серверы в другой стране | 0,60 | D16 (1), D19 (2), D20 (3) | D08, D04 | «в другой стране», «облачный провайдер» против «на территорию иностранного государства», «трансграничная передача», «иностранному лицу»; D08 — самый длинный документ корпуса |
| Q04 кредит без участия сотрудника | 0,00 | — | D09, D15, D28 | полный перефраз: «сама одобряет … без участия сотрудника» против «решение на основании исключительно автоматизированной обработки»; ни одного релевантного документа в топ-5 |
| Q05 вход по лицу | 0,33 | D14 (3) | D07, D11 | в вопросе нет юридического термина «биометрические данные»; слово «распознавание» уводит к документам AI Act (D24, D29) |
| Q06 оценка вреда до запуска | 0,33 | D10 (2) | D18, D28 | «оценить вред» совпадает со ст. 18.1 152-ФЗ, но в GDPR и AI Act это «оценка воздействия» и «высокий риск» |
| Q07 данные заказов для обучения | 0,20 | D25 (1) | D02, D03, D12, D13 | вопрос о конкретном случае, а ответ — общие принципы и основания («ограничение целью», «несовместимая с целями сбора»); «модель», «обучение» тянут документы AI Act (D21, D30) |
| Q08 чужая LLM через API | 0,60 | D30 (2), D21 (3), D29 (5) | D16, D04 | часть ответа неявная: в вопросе нет слов «персональные данные», а именно они делают применимыми ст. 28 GDPR и ст. 6 ч. 3 152-ФЗ |
| Q09 эмоции сотрудников | 0,40 | D29 (1), D23 (3) | D28, D14, D06 | «сотрудники» против «работники»; «выгорание» — это данные о здоровье, но слова «здоровье» в вопросе нет |
| Q10 ИИ для отбора резюме | 0,40 | D28 (3), D26 (5) | D22, D24, D27 | омоним: «резюме» кандидата совпало с «резюме о контенте» в ст. 53 — D30 на 1-м месте; общие слова «система», «использовать» есть во всех документах AI Act |

Типы ошибок:

1. **Перефраз и разрыв лексики** (Q03, Q04, Q05, Q06, Q07) — главная причина. BM25 учитывает только совпадение слов, а вопросы по требованию методички сформулированы своими словами.
2. **Бытовые и юридические синонимы** (Q02, Q03, Q09): подрядчик — процессор, сотрудник — работник, страна — государство. Словарь синонимов покрывает только роли из глоссария.
3. **Омонимия** (Q10): «резюме» кандидата и «резюме» обучающих данных.
4. **Шум от общих слов AI Act** (Q01, Q05, Q07, Q10): «система», «использование», «распознавание», «модель» встречаются во многих документах регламента.
5. **Длинные документы** (Q01, Q03): нормализация по длине понижает D03 и D08; изменение `b` эту проблему не решило (`--sweep`).
6. **Неявная часть ответа** (Q08, Q09): нужный документ связан с вопросом через вывод («через API уходят персональные данные», «выгорание — это здоровье»), а не через слова.

Возможные улучшения (не применялись, чтобы не подгонять результат под набор): синонимы из общей лексики (сотрудник — работник, страна — государство), проверенные на черновом наборе; деление длинных статей на части; расширение запроса с помощью LLM или гибридный поиск с векторными представлениями — за рамками требования курса реализовать BM25.

## Вывод о качестве ранжирования

Черновик по метрикам поиска; дополняется после прогона ответов LLM.

Итоговая конфигурация (лемматизация `pymorphy3`, стоп-слова, синонимы, `k₁ = 1,2`, `b = 0,75`) даёт на 10 вопросах Recall@5 = 0,37 и MRR = 0,60. В первые пять документов в среднем попадает чуть больше трети релевантных; в 9 вопросах из 10 хотя бы один релевантный документ есть в топ-5, в 4 — на первом месте. Для RAG это значит, что модель обычно получает часть нужных норм, но редко все: ответ по нескольким юрисдикциям чаще всего будет неполным, а на вопрос, описанный совсем своими словами (Q04), поиск может не дать опоры вовсе.

Лемматизация — главное улучшение (+0,08 Recall, +0,11 MRR): русская морфология без неё разрывает совпадения. Параметры BM25 почти не влияют. Основное ограничение — лексический разрыв между вопросом пользователя и текстом закона: лучше всего находятся вопросы с юридическим термином («трансграничная передача», «оценка воздействия», «модель общего назначения»), хуже всего — описания ситуаций своими словами и вопросы, где нужная норма связана с ситуацией через вывод.

Балл BM25 плохо отделяет вопросы без ответа: на черновом наборе их лучшие баллы (4,5–11,9) перекрываются с баллами обычных вопросов (3,6–16,5), а в основном наборе порог 3,0 отсекает лишь одну ловушку из пяти. Поэтому отказ по существу должна обеспечить LLM (`NO_ANSWER`).
