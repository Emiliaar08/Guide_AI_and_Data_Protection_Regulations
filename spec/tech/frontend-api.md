# Подключение интерфейса к API

Состояние на 24.11.2026. Фронтенд интегрирован с сервером из ветки `feature/api`; объединённая работа ведётся в `feature/frontend-api`. Python-модули API, поиска, ответов и корпус при интеграции не менялись. Полный контракт — в [architecture.md](architecture.md), текущее поведение экранов — в [описании интерфейса](../product/interface.md).

## Границы частей

- Эмилия: `app/index.html`, `app/styles.css`, `app/app.js`, `app/api.js`, `app/data.js`.
- Александра: сервер `app/server.py`, HTTP-контракт и вызов поиска и модели.
- Елена: `app/search.py`, корпус и проверка качества RAG.

Все сетевые запросы интерфейса проходят через `app/api.js`. Он по умолчанию обращается к `/api/search` на том же origin. Сервер FastAPI раздаёт и фронтенд, и API.

Для macOS добавлен `start.command`: он запускает существующий сервер и открывает HTTP-адрес приложения. Открытие `app/index.html` по `file://` перенаправляется на `http://localhost:4173` с сохранением раздела; отправка запросов из файлового origin не используется.

## Поиск и ответ — подключено

`POST /api/search`:

```json
{ "query": "Нужно ли согласие на обработку персональных данных?", "jurisdiction": null }
```

`query` — непустая строка до 2000 символов. `jurisdiction` — `ru`, `eu` или `null`. Фронтенд отправляет именно эти два поля. Сервер пока не принимает историю диалога, поэтому переписка сохраняется локально для пользователя, но не влияет на следующий запрос.

Ответ:

```json
{
  "status": "ok",
  "answer": "Ответ модели с метками [D13]",
  "clarification_question": null,
  "citations": [
    {
      "id": "D13",
      "doc_title": "GDPR (Регламент ЕС 2016/679)",
      "article": "ст. 6",
      "excerpt": "Фрагмент из корпуса",
      "jurisdiction": "eu",
      "edition": "Редакция документа в корпусе",
      "url": "https://eur-lex.europa.eu/eli/reg/2016/679/oj/eng"
    }
  ]
}
```

| Состояние | Поведение интерфейса |
|---|---|
| `ok` | Показывает `answer`, выделяет известные метки `[id]`, создаёт карточки цитат. Нажатие на метку раскрывает нужную карточку. |
| `insufficient` | Показывает `answer`, если он задан, иначе «В документах нет информации по этому вопросу». Это обычный ответ; кнопки повтора ошибки нет. |
| `need_clarification` | Показывает `clarification_question` как ответ в том же диалоге. |
| Ожидание | Показывает индикатор и кнопку остановки; параллельная отправка в том же чате блокируется. |
| `422` | Сообщает, что запрос должен содержать 1–2000 символов. |
| `502` | Сообщает о сбое поиска или модели и предлагает повторить запрос. |
| Сетевая ошибка | Сообщает об отсутствии связи с сервером и предлагает повтор. |
| Таймаут | Сообщает, что ответ не пришёл за отведённое время, и предлагает повтор. |
| Некорректный JSON/формат | Показывает ошибку формата; не создаёт пустой ответ. |

Таймаут запроса чата — 210 секунд, учитывая 180 секунд ожидания LLM на сервере. Кнопка остановки прерывает ожидание в браузере; остановка вычислений на сервере зависит от его реализации. Повтор использует тот же вопрос и выбранную при его отправке юрисдикцию.

Текст экранируется перед показом. Ссылки источников допускают только HTTP/HTTPS. Метка превращается в кнопку только при наличии цитаты с таким `id`. Текст, цитаты, вопрос и `id` сохраняются вместе при добавлении ответа в избранное.

## Каталог и локальные данные

`app/data.js` содержит метаданные 27 статей, сгруппированных из 30 фрагментов `corpus/docs.jsonl`. Поля `fragmentIds` связывают статьи с документами RAG. Ответы чата не формируются из этого каталога: они всегда запрашиваются у сервера.

Идентификатор карточки статьи и идентификатор фрагмента различаются. Например, карточка `152fz:6` объединяет `D03` и `D04`; метка в ответе ссылается именно на `D03` или `D04`. После изменения корпуса каталог `app/data.js` нужно сверять с новой версией `docs.jsonl`.

История, черновики и избранное хранятся в `localStorage`. Ранее сохранённые документы мигрируют в избранные статьи; существующие чаты сохраняются при обновлении интерфейса.

## Будущие маршруты

В текущем сервере отсутствуют маршруты авторизации, синхронизации истории и выдачи каталога. Интерфейс входа и регистрации сохранён. Для следующих этапов клиент поддерживает настройки:

```html
<!-- При обычном запуске добавлять настройки не требуется. -->
<script>
  window.NAVIGATOR_CONFIG = {
    chatEndpoint: '/api/search',
    authBase: '/api/auth',
    catalogEndpoint: '/api/catalog'
  };
</script>
```

Настройка располагается перед `api.js`. `authBase` и `catalogEndpoint` следует включать после появления соответствующих маршрутов.

План авторизации: `POST /api/auth/register`, `POST /api/auth/login`, `GET /api/auth/me` возвращают `{ "user": { "id": "...", "name": "...", "email": "..." } }`; сервер устанавливает сессию через cookie. `POST /api/auth/logout` завершает её (`204` либо `200` с JSON). Пароли и токены не сохраняются в браузерном хранилище.

План каталога: `GET /api/catalog` возвращает массивы `documents` и `articles` с полями, соответствующими `app/data.js`. У документа обязательны `id`, `short`, `title`, `jurisdiction`, `url`; у статьи — `id`, `documentId`, строковый `number`, `title`, `url`. Идентификаторы уникальны и стабильны; допускаются латинские буквы, цифры, `:`, `.`, `_` и `-`.

## Следующие шаги команды

Эти пункты требуют отдельной реализации или согласования. Текущий `/api/search` уже подключён.

| Задача | Кто участвует | Что требуется |
|---|---|---|
| Рабочая авторизация | Александра; подключение клиента — Эмилия | Реализовать `POST /api/auth/register`, `POST /api/auth/login`, `GET /api/auth/me`, `POST /api/auth/logout` по описанному выше формату; после этого включить `authBase` и проверить восстановление сессии |
| Учёт контекста чата | Александра и Елена; изменение запроса клиента — Эмилия | Согласовать поля предыдущих сообщений и способ их использования в RAG. Сейчас фронтенд отправляет только `query` и `jurisdiction` |
| История и избранное между устройствами | Александра; подключение — Эмилия | Согласовать серверные операции хранения; сейчас данные локальны для браузера |
| Обновление корпуса и каталога | Елена и Эмилия; при API каталога — Александра | Сохранять стабильные `D01`–`D30`, согласовывать новые `id` и обновлять карточки статей и `fragmentIds` |
| Сквозная проверка внешней LLM | Команда | Запустить интерфейс с настоящим поиском и настроенной серверной моделью; проверить ответы, отказ и соответствие меток цитат |

Для RAG сохраняется правило: метка `[D13]` в тексте ответа соответствует полю `id: "D13"` в `citations`. Карточка использует также `doc_title`, `article`, `excerpt`, `jurisdiction`, `edition` и `url`. Сохранение этих полей позволяет менять поиск и модель без переделки экранов.

## Проверенное состояние

- Существующий набор бэкенда, поиска и бенчмарка: 51 тест прошёл при интеграции.
- В браузере проверены реальный HTTP-запрос на заглушках сервера, отказ, ошибки 422/502, отсутствие связи, повтор без дубликата, таймаут и остановка ожидания.
- Проверен запрос через настоящий BM25 по корпусу с заглушкой LLM.
- Для `need_clarification` проверено отображение тестового ответа: текущее серверное правило этот статус не формирует.
- Прогон текущего интерфейса с внешней LLM ещё не выполнялся. Прогоны модели из `benchmark/results/` относятся к проверке серверного поиска и ответа.
